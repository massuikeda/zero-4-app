# 目標の構成への移行（段階的に進める）

`ネットワーク図_改.drawio` の「目標の構成」に、効果の大きい順に1段ずつ近づける。
1段ごとに動作を確認してから次へ進む（途中で止めても、その時点で動く状態を保つ）。

| 段 | やること | 守れるようになること | コードの変更 | 状態 |
|---|---|---|---|---|
| ① | 秘密（DBのパスワード・AIのキー）を Key Vault に移し、App Service はマネージドIDで読む | 秘密がアプリ設定・画面に見えなくなる。誰がいつ読んだか記録される | なし | **これから** |
| ② | MySQL・Azure OpenAI・Key Vault を閉じる（プライベートエンドポイント＋バックエンドのVNet統合＋プライベートDNSゾーン） | DB・AI にインターネットから届かなくなる | なし（設定だけ） | 未着手 |
| ③ | 入口に Application Gateway（WAF）を置き、銀行用の画面に IP 制限をかける | SQLインジェクションなどの攻撃・大量の通信を入口で止める | なし（設定だけ） | 未着手 |
| ④ | App Service を閉じる（入口は Application Gateway だけ）。デプロイは VNet の中のランナーから行う（`docs/RUNNER.md`） | アプリにも直接届かなくなる | workflow の変更（済み。変数 `DEPLOY_RUNNER` で切り替え） | ランナーの準備はできる |
| ⑤ | ログイン を Entra ID にする（仮のログインをやめる） | 本人確認ができる。①〜④の守りが意味を持つ | 画面・設定（作りはある） | 未着手 |

- ⑤（本物のログイン）は、本物の企業のデータを入れる前に必須。①〜④だけでは「URLを知っていれば誰でも入れる」状態は変わらない。
- 費用が大きいのは ③ の Application Gateway（WAF v2）。始める前に Azure の料金計算ツールで見積もる。①〜② の追加費用は小さい。
- ② 以降は、ネットワークの設定を変える権限（VNet・プライベートエンドポイントの作成）が必要。権限がなければ、管理者に依頼する。

## ① 秘密を Key Vault に移す

### 何が変わるか

| | 今 | ①のあと |
|---|---|---|
| DBのパスワード・AIのキーの置き場所 | `zero4-app-be` のアプリ設定（ポータルで見える） | Key Vault |
| アプリ設定に書くもの | 値そのもの | `@Microsoft.KeyVault(...)`（Key Vault のどこにあるかだけ） |
| バックエンドが値を読む方法 | 環境変数 | 同じ（App Service が Key Vault から取ってきて、環境変数として渡す） |

アプリのコードは変えない。App Service の「Key Vault 参照」という仕組みを使う。

### 手順

**1. Key Vault を作る**

- Azure ポータルで「キー コンテナー」を作成する
  - リソースグループ：App Service と同じ
  - リージョン：Japan East
  - 名前：例 `kv-zero4-app`（Azure 全体で一意。使われていたら末尾に数字を足す）
  - **アクセス構成（アクセス許可モデル）：「コンテナーのアクセス ポリシー」**
    - 「Azure ロールベースのアクセス制御（RBAC）」でもよいが、ロールの割り当てには「所有者」などの権限が要る。
      前にマネージドIDの設定で権限が足りなかったので、アクセス ポリシーのほうが確実
  - ネットワーク：今は「すべてのネットワーク」のまま（② で閉じる）

**2. 秘密を入れる**（Key Vault →「シークレット」→「生成/インポート」）

| 名前 | 値 |
|---|---|
| `db-password` | MySQL のパスワード（`.env` の `DB_PASSWORD` と同じ） |
| `azure-openai-api-key` | Azure OpenAI のキー（`.env` の `AZURE_OPENAI_API_KEY` と同じ） |

**3. バックエンドにマネージドIDを付ける**

- `zero4-app-be` →「設定」→「ID」→「システム割り当て済み」→ 状態を「オン」→ 保存

**4. バックエンドに、秘密を読む許可を出す**

- Key Vault →「アクセス ポリシー」→「作成」
  - シークレットのアクセス許可：**取得** と **一覧** だけにチェック（ほかは付けない）
  - プリンシパル：`zero4-app-be` を検索して選ぶ
  - 作成

**5. アプリ設定を Key Vault 参照に変える**（`zero4-app-be` →「環境変数」）

| 名前 | 新しい値 |
|---|---|
| `DB_PASSWORD` | `@Microsoft.KeyVault(VaultName=kv-zero4-app;SecretName=db-password)` |
| `AZURE_OPENAI_API_KEY` | `@Microsoft.KeyVault(VaultName=kv-zero4-app;SecretName=azure-openai-api-key)` |

`kv-zero4-app` は、1 で付けた名前に置き換える。保存すると App Service が再起動する。

### 確認

1. 「環境変数」の一覧で、2つの値の横に **緑のチェック（Key Vault 参照：解決済み）** が出ている
   - 赤い×なら、4 の許可か、5 の名前のつづりを見直す
2. `<バックエンドのURL>/api/health` が `{"status":"ok","db":"mysql",...}` を返す（DB のパスワードが読めている）
3. 画面のヒアリングタブで「AIでAS-ISを作成」を試し、エラーにならない（AI のキーが読めている）

### うまくいかないとき

- 値を元に戻せば（パスワード・キーをそのまま入れ直せば）、すぐ今の状態に戻る
- Key Vault の秘密を変えたあとは、App Service を再起動すると新しい値が読まれる（自動の更新は最大24時間かかる）

### このあと

- 秘密の値は、Key Vault にしか置かない。パスワードを変えるときは、MySQL と Key Vault の2か所を変える
- `.env`（ローカル）はこれまでどおり。Key Vault 参照は Azure の上だけで働く
